18.1Rule-based metrics

18.1.1BLEU (BiLingual Evaluation Understudy)

BLEU evaluates how similar a machine-generated text is to one or more reference texts, mainly using n-gram precision.

It checks: How many words/phrases in the output also appear in the reference.

BLEU=BP×exp(n=1∑N​wn​log⁡pn​)
Where:

  • pn​= modified n-gram precision

  • wn​= weight (usually equal)

  • BP= brevity penalty (penalizes very short outputs)

18.1.2ROUGE (Recall-Oriented Understudy for Gisting Evaluation)

ROUGE focuses on recall, i.e., how much of the reference text is covered by the generated text.

Commonly used in, Summarization and Text generation evaluation

ROUGE-N=∣Reference n-grams∣∣Overlapping n-grams∣​

Set-based notation

ROUGE-N=∣Greference(n)​∣∣Ggenerated(n)​∩Greference(n)​∣​

Where G(n)denotes the set of n-grams.

18.1.3METEOR (Metric for Evaluation of Translation with Explicit Ordering)

METEOR evaluates translation quality by considering

  • Exact word matches

  • Stem matches

  • Synonym matches

  • Word order

METEOR=Fmean​×(1−Penalty)

Fmean​=R+9P10×P×R​

  • P= Precision

  • R= Recall

  • Penalty = fragmentation penalty for word order

18.2LaaJ (LLM-as-a-Judge)

Use LLM to rate the quality of the response

  • No need for reference/label

  • Interpretability via rationales

18.3Variations of LaaJ (LLM-as-a-Judge)

18.4Biases

a) Position Bias

The model gives higher importance to items appearing earlier (or later) in a list, even when all items are equally good.

Remedy

  • Take the average: Evaluate the same content in different orders and average the scores.

  • Tweak position embeddings: Reduce the model’s sensitivity to order so position does not dominate judgment.

b) Verbosity Bias

The model tends to prefer longer answers, assuming they are better, even if they contain unnecessary or repeated information.

Remedy

  • Provide explicit length guidelines (e.g., “be concise”).

  • Use few-shot examples showing good short answers.

  • Apply a penalty on output length to discourage unnecessary verbosity.

c) Self-Enhancement Bias

The model favors its own generated answers or similar styles, judging them as better than others.

Remedy

  • Do not let the model act as both generator and judge (🤖 ≠ ⚖).

  • Use separate evaluation models or human evaluators.

18.5Best practice

  • Crisp Evaluation Guidelines are clear, simple, and unambiguous rules used to evaluate model outputs consistently and fairly, while minimizing bias and randomness.

  • Use a binary scale: Prefer simple scales (e.g., correct / incorrect) over complex multi-level scoring to reduce ambiguity.

  • Write rationale before the score: Force the model to explain its reasoning first, then give a score. This improves consistency and reduces bias.

  • Calibrate with human judgments: Regularly compare model scores with human evaluations to align model behavior with real expectations.

  • Use low temperature: A low temperature setting reduces randomness and ensures Stable scores, Better reproducibility and More consistent evaluations

18.6Factuality

Factuality means how correct and truthful a model’s output is with respect to real-world facts or given source data.

In simple words: Does the answer state facts that are true and supported by evidence?

Step 1: Generate the Answer

Example answer: “Tokyo is the capital of Japan and has a population of 50 million.”

Step 2: Decompose into Atomic Facts

Split the answer into independent factual claims

  • Tokyo is the capital of Japan.

  • Tokyo has a population of 50 million.

Each fact must be

  • Checkable

  • Independent

  • Atomic (cannot be split further)

Step 3: Verify Each Fact

Each fact is checked against

  • Ground truth

  • Retrieved documents

  • Trusted sources

Fact True / False
Tokyo is the capital of Japan True
Tokyo population is 50 million False

Step 4: Compute Factuality Score

Factuality Score=Total number of extracted factual statementsNumber of factually correct statements​
Example:

Factuality=21​=0.5

18.7Hallucination Analysis

A hallucination occurs when a Large Language Model generates confident but incorrect, fabricated, or unverifiable information that is not grounded in the input, training data, or real-world facts.

Example:
Asking an LLM for a non-existent research paper and it produces a fake title, authors, and DOI.

Causes of Hallucinations

Training Data Limitations

  • Incomplete, outdated, or noisy datasets

  • Missing domain-specific knowledge

  • Overrepresentation of patterns instead of facts

Next-Token Prediction Objective

  • LLMs optimize:

P(xt​∣x1:t−1​)

  • They aim for plausibility, not truth

Lack of Grounding

  • No access to:

    • Databases

    • APIs

    • Real-time sources

  • Purely parametric memory

Prompt Ambiguity

  • Vague or underspecified prompts

  • Missing constraints or context

Overgeneralization

  • Applying known patterns to unseen or edge cases

Decoding Strategy Issues

  • High temperature or top-p sampling

  • Aggressive creativity

Fine-Tuning Errors

  • Poor-quality instruction data

  • Reinforcing wrong answers during RLHF

Detection Methods

Human Evaluation

  • Expert fact-checking

  • Cross-verification with trusted sources

Self-Consistency Checks

  • Ask the model the same question multiple times

  • Compare outputs for contradictions

  • High variance → potential hallucination

External Knowledge Verification

  • Cross-check with:

    • Knowledge graphs

    • Search engines

    • Databases (Wikipedia, PubMed, etc.)

Confidence–Uncertainty Mismatch

  • Very confident tone with no citations

  • Over-specific details without sources

Entropy / Log-Probability Analysis

  • Low confidence tokens (high entropy)

  • Sudden probability drops in generation

Adversarial Questioning

  • Ask follow-ups like:

    • “Provide sources”

    • “Explain your reasoning”

    • “Verify this claim”

Automated Hallucination Classifiers

  • Models trained to label outputs as:

    • Factual

    • Unsupported

    • Hallucinated

  • Examples: factuality classifiers, NLI-based checks.

Common issues

Modeling

  • Weak reasoning, grounding capabilities

  • Too much going on in the context window

  • Tool modeling isn't right

Tool

  • Tool itself has a problem

  • Output of the tool isn't interpretable

18.8Pareto frontier

The Pareto frontier (or Pareto front) is a concept from multi-objective optimization that represents the set of best possible trade-offs between two or more conflicting objectives.

Possible trade-offs.

  • quality vs. cost/latency

  • quality vs. safety

  • quality vs. context length

18.9Diffusion in LLMs

Diffusion in LLMs refers to using diffusion-based generative modeling—a technique originally popular in image generation—to generate or refine text by gradually denoising it over multiple steps, instead of predicting the next token in a single left-to-right pass.

In short: text is generated by iteratively improving a noisy representation, not token-by-token autoregression.

Traditional LLM vs Diffusion-based LLM

Autoregressive LLMs (GPT-style)

  • Generate text one token at a time

  • Strict left-to-right order

  • Errors can propagate forward

Diffusion-based LLMs

  • Start with noise

  • Iteratively denoise the whole sequence

  • Can revise all tokens at once

How Diffusion Works (Intuition)

  • Start with a clean text

  • Gradually add noise during training

  • Train a model to remove noise step by step

  • At inference:

    • Start from pure noise

    • Repeatedly denoise until readable text emerges
