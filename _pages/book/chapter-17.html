17.1Retrieval-Augmented Generation

Retrieval-Augmented Generation (RAG) is an AI approach that combines information retrieval with text generation so a language model can give more accurate, up-to-date, and grounded answers.

Why do we need RAG?

A normal LLM (like GPT) has problems

  • Knowledge is frozen at training time

  • Can hallucinate facts

  • Cannot access private or domain-specific data

  • Long documents don’t fit fully in context

RAG solves this by letting the model “look up” information before answering.

Simple intuition (human analogy)

Think like a student in an exam

  • Without RAG → Answer from memory only

  • With RAG → First open book → read relevant pages → then answer

  • So: RAG = Search first, then generate

Formal definition

Retrieval-Augmented Generation is a framework where a language model retrieves relevant external documents from a knowledge source and then uses them as context to generate a response.

Core components of RAG

Knowledge Source

This can be

  • PDFs

  • Research papers

  • Web pages

  • Databases

  • Tweets / social media data

  • Internal company documents

Retriever (Search Engine)

The retriever finds relevant chunks for a query.

Common methods

  • Vector search (most popular)

  • BM25 (keyword-based)

  • Hybrid (BM25 + vectors)

Uses embeddings

Query → embedding → similarity search

Generator (LLM)

The generator

  • Takes query + retrieved documents

  • Produces a final answer

Example 1

User question: “What are the limitations of BERT in long document classification?”

With RAG

17.1.1Retrieve

  • Research papers on BERT

  • Longformer, BigBird comparisons

  1. Feed retrieved text to LLM

  2. Generate a grounded answer

17.2How documents are prepared (important)

Step 1: Chunking

Large documents → small chunks (e.g., 300–500 tokens)

Step 2: Embedding

Each chunk converted to a vector

text → embedding model → vector

Step 3: Store in Vector DB

  • FAISS

  • Pinecone

  • Weaviate

  • Chrom

Pseudo-code example (conceptual)

query = "What is RAG?"
query_vector = embed(query)
docs = vector_db.search(query_vector, top_k=5)
context = concatenate(docs)
answer = LLM.generate(prompt = context + query)

17.3Retrieval overview

Step 1 – Candidate Retrieval (in RAG)

Select a small set of potentially relevant documents (candidates) from a large knowledge base that are most likely to help answer the user query.

Key idea: It is better to retrieve “possibly useful” documents than to miss an important one.

This step only retrieves candidates.

Method 1: Semantic Search (Embeddings-based Similarity)

Documents and queries are converted into dense vectors (embeddings).
Similarity is computed using:

  • Cosine similarity

  • Dot product

  • Euclidean distance

How it works

  • Convert query → vector

  • Convert document chunks → vectors

  • Retrieve top-k closest vectors

Method 2: Keyword Search (BM25)

A lexical retrieval method based on

  • Term frequency

  • Inverse document frequency

  • Document length normalization

How it works

Documents are ranked by keyword overlap with the query.

Method 3: Hybrid Search (Semantic + BM25)

Combines semantic similarity and keyword matching into a single ranking.

Typical scoring

Final Score = α × SemanticScore + (1 − α) × BM25Score

Improvements applied before or during retrieval

17.3.1Mitigate Discrepancy in Nature of Embeddings

Problem

  • Query embeddings ≠ Document embeddings

  • Queries are short

  • Documents are long and descriptive

  • This mismatch reduces similarity accuracy.

Solution: Make query and document embeddings more comparable.

17.3.2Contextualize Document Chunks

Problem: Documents are split into chunks → loss of context.

Solution: Add surrounding context or metadata.

Step 2 – Ranking (Re-ranking in RAG)

Assign a final relevance score to retrieved candidates using a more powerful model, and select the best chunks to pass to the LLM.

Step-1 retrieves many “possibly relevant” chunks; Step-2 precisely orders them.

Why Re-ranking Is Needed

  • Initial retrieval favors speed

  • Re-ranking favors accuracy

  • Embedding similarity alone is not enough

Example

  • Chunk A: semantically similar but vague

  • Chunk B: exact answer but less semantic overlap

Re-ranker promotes Chunk B

A re-ranker is a cross-encoder or interaction model that jointly processes

(Query, Document Chunk) → Relevance Score

Typical models

  • BERT cross-encoders

  • MonoT5

  • LLM-based scoring

  • Instruction-tuned rankers

How Re-ranking Works (Setup)

  • Retrieve top-N chunks (e.g., N=50)

  • For each chunk:

  • score_i = Ranker(query, chunk_i)

  • Sort by score

  • Select top-k (e.g., k=5)

Quantifying Retrieval & Ranking Performance

Measure how well retrieved and ranked chunks match ground-truth relevance.

Setup: Relevance Evaluation

For a query

  • We have retrieved k chunks

  • Each chunk is labeled:

  • Relevant (1)

  • Not relevant (0)

  • Or graded relevance (0–3)

Example relevance labels

[3, 2, 0, 1, 0]

Precision@k

It measures how many retrieved chunks are relevant

Precision@k=k∣{relevant items in top k}∣​
Example Top-5 chunks → 3 relevant

P@5=53​=0.6
High precision = less noise

Recall@k

It measures how many of all relevant chunks were retrieved

Recall@k=∣{all relevant items}∣∣{relevant items in top k}∣​

Example

Total relevant chunks = 6 Retrieved relevant = 3

R@5=63​=0.5
High recall = fewer misses
RAG favors high recall early

Reciprocal Rank@k (RR@k)

It measures how early the first relevant chunk appears

RR@k=rank of first relevant result1​

Example First relevant chunk at rank 2

RR@k=21​=0.5

If at rank 1

RR=1.0

Normalized Discounted Cumulative Gain@k (NDCG@k)

It measures quality of ranking with graded relevance

Rewards

  • Higher relevance

  • Higher position

Step 1: DCG@k

Measures the usefulness of retrieved results by rewarding highly relevant items placed at top ranks and penalizing relevant items that appear lower in the ranking.

DCG@k=i=1∑k​log2​(i+1)2reli​−1​

Step 2: IDCG@k (Ideal DCG)

Represents the maximum possible DCG obtained when results are perfectly ranked by relevance, used as a normalization reference.

Step 3: NDCG@k

Normalizes DCG by dividing it by IDCG, producing a score between 0 and 1 that reflects how close the ranking is to the ideal order.

NDCG@k=IDCG@kDCG@k​

Example

Relevance labels (top-5)

[3, 2, 0, 1, 0]

  • Higher score for putting 3 at rank 1

  • Penalizes relevant chunks placed lower

NDCG ∈ [0, 1]

17.4Tool calling

Tool calling allows a language model to invoke external tools (APIs, functions, services, or software) while solving a task, instead of relying only on its internal knowledge.

Tool calling enables autonomous systems to complete complex, real-world tasks by dynamically accessing and acting upon external resources.

Why Tool Calling Is Needed

LLMs by themselves

  • Cannot browse the web

  • Cannot run code

  • Cannot send emails

  • Have a knowledge cutoff

  • Cannot access private or live data

Tool calling extends the LLM’s capabilities beyond text generation.

How Tool Calling Works (High-Level Flow)

  • User gives a task

  • LLM decides:

    • Can I answer directly?

    • Do I need a tool?

  • If needed:

    • LLM selects the correct tool

    • Provides structured input

  • Tool executes and returns output

  • LLM uses the output to continue reasoning or respond

User → LLM → Tool → Result → LLM → Final Output

17.4.1Teach a Model to Use a Tool

The model must learn

  • When to use a tool

  • Which tool to use

  • How to format inputs

  • How to interpret outputs

Method 1: Teaching via Training

The model is trained on examples where

  • Provide the model with a user request as input.

  • Provide the correct tool call (tool name + arguments) as the target output.

  • The model predicts a tool call.

  • Compare the model’s prediction with the ground-truth tool call.

  • Compute loss and update model weights.

  • Repeat over many examples until the model learns when and how to call tools correctly.

Example (training sample)

User: What is 23 × 47?
Model: CALL calculator(23,47)
Tool Output: 1081
Model: The result is 1081.

Method 2: Teaching via Prompting

The model is not retrained.
Instead, tools are described in the system prompt.

Example prompt instruction

You can use the following tools:
- calculator(a, b)
- search(query)
Use them when needed.

17.4.2Examples of Common Use Cases

Information Retrieval

Used when the model needs external or updated information.

Examples

  • Web search

  • Database queries

  • Weather APIs

  • Stock price trackers

  • Searching a codebase

Computation

Used for precise or large-scale calculations.

Examples

  • Calculator

  • Python code execution

  • Data analysis scripts

Action (Real-World Interaction)

Used when the model must do something, not just answer.

Examples

  • Send emails

  • Send messages

  • Schedule meetings

  • Update files

  • Control software actions

17.4.3Benefits

  • LLMs become far more useful

  • Can interact with real-world systems

  • Solve tasks beyond language

  • Overcome knowledge cutoff

  • Enable autonomous agents

Challenges

  • More tools → lower accuracy

    • Tool selection becomes harder

  • Finite context length

    • Cannot describe unlimited tools

  • Tool definition overhead

    • Each tool needs schema, documentation, testing

17.4.4Tool Selection

Goal

  • Reduce latency

  • Improve accuracy

Problem: If many tools exist, the model

  • Takes longer to decide

  • Makes more mistakes

Solution

  • Narrow tool availability per task

  • Use routing models

  • Tool ranking and filtering

17.4.5Standardization: MCP (Model Context Protocol)

A standard protocol that defines how tools and data sources connect to LLMs. Connect tools and data to LLMs in a consistent, reusable, standardized way.

What MCP Standardizes

  • Tool interfaces

  • Input/output schemas

  • Authentication

  • Context injection

17.5Agents

An agent is a system that autonomously pursues goals and completes tasks on a user's behalf.

An agent is an AI system that can

  • Reason about a goal

  • Decide actions

  • Use tools

  • Observe results

  • Iterate until the goal is achieved

Goal → Reason → Act → Observe → Reason → Act → ... → Done

17.5.1ReAct

ReAct = Reason + Act

ReAct is a framework that interleaves reasoning and action, rather than separating them.

The model explicitly reasons about what to do before taking an action, and then reasons again after seeing the result.

ReAct Process (Step by Step)

Each iteration has three key elements

  • Thought (Reasoning) (What do I need to do next?)

  • Action (Call a tool)

  • Observation (Tool result)

Then the cycle repeats.

Example: ReAct in Action

Goal: “What is the current weather in Tokyo, and should I carry an umbrella?”

Step 1: Reason

Thought: I need current weather data for Tokyo. This requires a weather API.

Step 2: Act

Action: call weather_api(city="Tokyo")

Step 3: Observe

Observation: Rain, 80% chance, temperature 18°C

Step 4: Reason again

Thought: It is raining with high probability. I should recommend an umbrella.

Step 5: Final Answer

“It’s raining in Tokyo with an 80% chance of rain. You should carry an umbrella.”

ReAct vs Traditional Tool Calling

Aspect Tool Calling ReAct
Reasoning Implicit Explicit
Actions One-shot Iterative
Adaptation Limited Strong
Error recovery Poor Good

17.6Standardization: A2A (Agent-to-Agent)

A2A = Agent2Agent refers to a system where multiple AI agents communicate and collaborate to solve a task, instead of a single agent doing everything.

Think of it as a team of specialized agents working together.

In A2A systems

  • Each agent has a role (specialization)

  • Agents exchange messages

  • Agents delegate subtasks

  • A final result emerges from coordination

User Goal
↓
Coordinator Agent
↓
┌───────────┬───────────┬───────────┐
│ Research │ Analysis │ Action │
│ Agent │ Agent │ Agent │
└───────────┴───────────┴───────────┘
↓
Agent-to-Agent Communication
↓
Final Response

A2A Communication Process

  • Coordinator agent receives the task

  • Task is decomposed into subtasks

  • Subtasks are assigned to specialized agents

  • Agents communicate results to each other

  • Coordinator integrates outputs

  • Final answer is produced

17.6.1Risks

  • Agents can cause real-world harm if misused.

  • Example: data exfiltration, where sensitive data is accessed or leaked without permission.

Remediations

  • Training steps: Teach models safe behavior during training.

  • Inference safeguards: Apply safety checks while the model is running.

  • Benchmarks: Use evaluation tools such as Agent-SafetyBench to test and measure agent safety.

17.7Advanced RAG

Since you’re into agentic AI & explainability, note
