13.1Language Model

A language model (LM) is a mathematical or computational model that learns patterns in language and assigns probabilities to sequences of words or tokens.

Its main goal is to predict the next word (or token) given the previous ones.

OR

A language model estimates how likely a sequence of words is and can generate text by predicting the next word based on context.

Example:
If the input is: “I am learning machine …”

A language model might predict: “learning”

13.2Large Language Model

A Large Language Model (LLM) is a type of language model that:

  • Is built using deep neural networks (usually Transformers)

  • Has very large numbers of parameters (millions to hundreds of billions)

  • Is trained on massive text datasets

  • Can perform many language tasks without task-specific training

Popular LLMs

  • GPT-3 / GPT-4 / GPT-5 (OpenAI)

  • BERT (Google)

  • PaLM (Google)

  • Gemini (Google DeepMind)

  • LLaMA / LLaMA-2 / LLaMA-3 (Meta)

  • Claude (Anthropic)

  • Mistral (Mistral AI)

Open-source LLMs

  • LlaMA

  • Mistral

  • Falcon

  • BLOOM

13.3What is MoE (Mixture of Experts)?

Mixture of Experts (MoE) is a learning architecture where, instead of one single model handling all inputs, we have multiple specialized sub-models (called experts), and a gating network (router) decides which expert(s) should process each input. OR

MoE is a model that learns to divide the problem into parts and assigns each part to a specialized expert.

Example: Imagine a hospital:

Input Expert
Heart problem Cardiologist
Brain problem Neurologist
Skin problem Dermatologist

  • You (input) do not see all doctors.

  • A receptionist (gating network) routes you to the best expert.

MoE-based learning means:

  • The model learns experts and routing jointly

  • The system automatically decides:

    • What each expert specializes in

    • Which expert handles which input

In LLMs:

  • Experts replace FFN layers

  • Transformer attention stays the same

  • Each token is routed independently

Token → Attention → MoE FFN → Next Layer

13.3.1Dense MoE

Dense MoE is a Mixture of Experts model where all experts are activated for every input, and their outputs are combined using weights from a gating network. So:

  • You still have multiple experts

  • You still have a router (gate)

  • BUT no expert is skipped

Simple Analogy (Classroom)

Imagine:

  • 3 teachers (experts)

  • 1 student (input)

Dense MoE:

  • The student asks all teachers

  • Each teacher gives an answer

  • A coordinator (gate) decides how much to trust each teacher

  • Final answer = weighted mix of all answers

y​=i=1∑N​gi​(x) fi​(x)​

Where:

  • x= input

  • gi​(x)= gate weight for expert i

  • fi​(x)= output of expert i

  • y​= predicted output

13.3.2Sparse MoE

Modern LLMs use Sparse MoE:

  • Only Top-K experts are activated (usually K=1 or 2)

  • Saves computation

Sparse MoE. Output is the weighted average of selected expert outputs.

y​=i∈Top-K(g(x))∑​gi​(x) fi​(x)​

Where:

  • Only the top K experts (by gate score) are used

  • All other experts are ignored (weight = 0)

13.3.3How Training Works in MoE (Mixture of Experts)

In an MoE model, three things are learned simultaneously:

  • Expert parameters

    θ1​,θ2​,…,θN​

  • Gating (router) parameters

    Wg​

  • Shared layers (e.g., attention in transformers)

Loss Computation

Compare the prediction with the true label y:

Ltask​=l(y​,y)

Backpropagation in MoE

Gradients flow through two paths:

  • Expert Gradients: Only selected experts receive gradients:

∂θi​∂L​if expert i is used
Unused experts get zero gradient.

  • Router (Gate) Gradients: The gate also gets gradients:

∂Wg​∂L​
This teaches the router: Which inputs should go to which experts

13.3.4MoE Key Problem: Routing Collapse

Routing collapse occurs when the gate directs almost all inputs to a small subset of experts, while other experts are rarely or never utilized.

For example Gate outputs:

  • g(x)=[0.95, 0.03, 0.01, 0.01 ]
    Expert 1 gets 95% of tokens

  • Experts 2–4 starve

  • Those experts stop learning

13.3.5Solution: Load-Balancing Loss

  • Add an Auxiliary Loss

Total loss:

L=Ltask​+λ Lbalance​​

Lbalance​=Ni=1∑N​(fraci​⋅probi​)

Where:

  • fraci​: fraction of tokens routed to expert i

  • probi​: average gate probability for expert i

  • N: number of experts

  • Capacity Constraints

Limit tokens per expert:

capacity=α⋅NT​
Overflow tokens are rerouted or dropped.

  • Noisy Gating

Add noise before softmax:

g(x)=softmax(Wg​x+ϵ)
Prevents early dominance.

  • Expert Dropout: Randomly disable experts during training.

  • Warm-Up Dense Training: Start with dense MoE → switch to sparse.

13.4Next-Word Prediction (Core Idea)

A language model predicts the next token by producing a probability distribution:

P(wt+1​∣w1​,…,wt​)

Example Setup

Vocabulary: {eat, sleep, code, pizza, <EOS>}

Input prompt: “I like to”

The model outputs probabilities for the next word:

Word Probability
eat 0.40
sleep 0.30
code 0.20
pizza 0.07
<EOS> 0.03

13.4.1Greedy Decoding

Always pick the word with the highest probability at each step.

Formula

wt+1​=argwmax​P(w∣context)

Limitations of Greedy Decoding

  • Myopic (short-sighted)

  • Can miss better overall sentences

  • Repetitive and boring

  • Not good for creative tasks

13.4.2Beam Search

Keep the top K most probable partial sentences at each step and expand them.

score=t∑​logP(wt​∣w<t ​)

Example (Beam width = 2)

Step 1 (keep top 2 words)

Word Prob
eat 0.40
sleep 0.30

Beams:

  1. I like to eat
  2. I like to sleep

Step 2 (expand both)

From “eat”:

  • eat pizza → 0.40 × 0.60 = 0.24

  • eat <EOS> → 0.40 × 0.20 = 0.08

From “sleep”:

  • sleep now → 0.30 × 0.70 = 0.21

  • sleep <EOS> → 0.30 × 0.30 = 0.09

Keep top 2:

  1. eat pizza (0.24)

  2. sleep now (0.21)

Step 3

  • eat pizza <EOS> → 0.24 × 0.90 = 0.216

  • sleep now <EOS> → 0.21 × 0.80 = 0.168

Final Output (Beam Search)

I like to eat pizza (Chosen because total probability is higher)

Limitations of Beam Search

  • Expensive (slower)

  • Still deterministic

  • Often produces generic text

  • Poor diversity

13.4.3Sampling (Stochastic Decoding)

Randomly sample the next word according to its probability.

wt+1​∼P(w∣context)

Limitations of Sampling

  • Can generate nonsense

  • Inconsistent quality

  • Not reproducible

  • Needs controls (temperature, top-k, top-p)

13.5What Is Temperature?

Temperature controls how random or deterministic the model’s next-word choice is.

Low temperature → safer, more deterministic
High temperature → more random, more creative

13.5.1Where Temperature Is Applied?

A language model outputs logits (raw scores) for each word:

z=[z1​,z2​,…,zV​]

Temperature rescales logits before softmax:

P(wi​)=∑j​ezj​/Tezi​/T​

Where:

  • T= temperature

  • T>1→ more randomness

  • T<1→ less randomness

13.5.2Example Setup

Prompt: “I like to”

Model logits

Word Logit
eat 4.0
sleep 3.0
code 2.0
pizza 1.0

Scale logits

z/T=[4.0/1.0, 3.0/1.0, 2.0/1.0, 1.0/1.0]

z/T=[4.0, 3.0, 2.0, 1.0]

P(w)=softmax(z)

13.6What is Guided Decoding?

Guided decoding means steering the model’s next-word choices using extra rules or signals, instead of letting it rely only on probabilities.

Normal decoding: choose words only by probability
Guided decoding: choose words by probability plus guidance

Guidance can be:

  • Keywords to include/avoid

  • Style or format constraints

  • Biasing certain words

  • External scores (rules, classifiers)

Core Idea (Mathematical View)

A language model gives logits zi​. Guided decoding modifies these logits before softmax:

zi′​=zi​+bi​​

Where:

  • zi​= original logit

  • bi​= guidance bias (positive or negative)

Then:

P(wi​)=softmax(zi′​/T)

Example: Keyword-Guided Decoding (Encourage a Word)

Prompt: “I like to”

Model logits:

Word Logit z
eat 4.0
sleep 3.0
code 2.0
pizza 1.0

Goal

Force the model to prefer “code”

Step 1: Add positive bias

b=[0, 0, +2, 0]

z=[4.0, 3.0, 2.0, 1.0]

z′=z+b=[4, 3, 4, 1]

Step 2: Apply temperature

z′/T

Comparison with Other Decoding

Method Control Flexibility
Greedy ❌ Low
Beam Search ❌ Low
Sampling ❌ High
Guided Decoding ✅ High

13.7Prompting Strategies

Prompting strategies are ways of writing prompts so the model gives better, more reliable outputs. Good prompting gives the model context, structure, and constraints so it can use its knowledge effectively.

Section Content
Context My teddy bear had a long day and needs a bedtime story.
Instructions Generate a bedtime story that takes place in a specific location.
Input Location: Country of Teddy Bears
Constraints The story needs to be suitable for teddy bears that are tired.

Beware of “Context Rot” ⚠️

Context rot happens when a prompt or conversation becomes too long, messy, or overloaded, causing the model to lose focus, forget earlier constraints, or mix unrelated instructions.

13.8In-Context Learning (ICL)

In-context learning is when a language model learns how to perform a task from examples given inside the prompt, without changing its weights.

The model does not train — it infers the pattern from context.

ICL Type How It Works Example Prompt (Short) Example Output Limitations
Zero-Shot ICL Model uses only instructions, no examples, relying on prior knowledge. “Translate to French: Good morning” Bonjour Lower accuracy on complex or ambiguous tasks; sensitive to wording.
One-Shot ICL Model infers the task from one example in the prompt. Hello → BonjourGood night → Bonne nuit One example may not capture full pattern; brittle.
Few-Shot ICL Model learns pattern from multiple examples. Cat → AnimalRose → PlantEagle → Animal Uses more context; too many examples can confuse.
Chain-of-Thought ICL Examples include step-by-step reasoning, guiding logic. 2+3=5 (step shown)4+6=? 10 (with steps) Longer outputs; reasoning can still be wrong.
Self-Consistency ICL Model generates multiple reasoning paths and selects the most common answer. Solve 3 times and give final answer Most frequent answer High compute cost; slower.
Role-Based ICL Prompt assigns a role/persona to shape behavior. “You are a math teacher. Explain fractions.” Simple explanation Role confusion if combined with many constraints.
Format-Based ICL Examples show exact output structure to follow. Name: AliAge: 20Name: Sara Structured output Breaks if format is too strict or complex.
Constraint-Driven ICL Examples include rules or limits (length, tone). “Answer in one sentence” Short response Conflicting constraints cause failures.
Retrieval-Augmented ICL External info is included as context for the task. “Using the text below…” Context-based answer Limited by context window; noisy data hurts.

13.9What is Inference Optimization?

Inference is to generate outputs (e.g., next token in an LLM) using a trained model.

Inference optimization is making inference faster, cheaper, and using less memory without retraining (or with minimal changes).

Main Challenges

  1. Autoregressive generation

    • Tokens are generated one by one

    • Each new token reuses all previous context

  2. Attention cost grows with sequence length

    • Attention is O(n²) in memory and compute

  3. Memory bottlenecks

    • KV cache becomes huge for long prompts and many users

  4. Hardware underutilization

    • GPU waits because decoding is sequential

13.10Two Classes of Inference Optimizations

Category Meaning
Exact efficiency Same output, just faster
Approximations Slightly different output, much faster

13.10.1Exact Efficiency (No Output Change)

KV Cache (Avoid Redundancies)

Self-attention uses three vectors for each token:

  • Q (Query) → what I’m looking for now

  • K (Key) → what each past token offers

  • V (Value) → information carried by each past token

Without caching, the model recomputes attention for all past tokens every step.

Idea: Store Key (K) and Value (V) vectors from previous tokens and reuse them.

Simple example of Sentence generation

"I love deep learning"

Tokens (generated one by one):

  1. I

  2. love

  3. deep

  4. learning ← current token

Step 1: When token = "I"

Only one token exists.

QI, KI, VI computed
Attention(QI, KI, VI)

Nothing to cache yet.

Step 2: When token = "love"

Without cache:

  • Recompute K₁, V₁ again ❌

With KV cache:

  • Reuse K₁, V₁ ✅

Q_{love} (new)
K_{I}, V_{I} (cached)
K_{love}, v_{love} (new)

Attention:

Qlove​⋅[KI​,Klove​]

Step last: When token = " learning"

For "learning":

  • Use cache KI​, Klove​, Kdeep​ and VI​, Vlove​, Vdeep​

  • Compute Qlearning​ (must be new)

  • Compute Klearning​ , Vlearning​ (and store them)

Scores=Qlearning​⋅​KI​Klove​Kdeep​Klearning​​​

Benefit

  • Compute drops from O(n²) → O(n)

  • Huge speedup for long sequences

Limitation

  • KV cache grows linearly with sequence length → memory problem

2. PagedAttention(Memory Management )

KV cache stored as one contiguous block:

  • Fragmentation

  • Waste when sequences end

  • Hard to scale to thousands of users

Idea (inspired by OS virtual memory):

  • Split KV cache into fixed-size pages

  • Pages can be reused, swapped, or freed

Example Analogy: Think of KV cache like books:

Without paging:

  • One giant shelf per user

  • Half-empty shelves waste space

With paging:

  • Small standard boxes

  • Boxes are reused when a user finishes

Speculative Decoding (Reformulate the Math)

Autoregressive decoding is sequential → GPU underutilized

Idea: Speculative Decoding

  • Use a small fast model to guess multiple tokens

  • Verify guesses using the large model

Small model proposes: "The cat is sleeping on the"

Large model checks:

  • If tokens match → accept all at once

  • If mismatch → roll back

Cost

  • Requires two models

  • Extra engineering complexity

13.10.2Approximations (Trade Accuracy for Speed)

Attention Head Sharing (Architectural Changes)

Attention Head Sharing is an inference optimization idea where multiple attention heads share the same Key (K) and Value (V) representations instead of each head having its own. The goal is to reduce memory usage (KV cache) and speed up inference, especially for long sequences.

a) Multi-Head Attention (MHA)(Standard self-attention in a transformer)

  • Each layer has multiple attention heads

  • Each head computes its own:

    • Query (Q)

    • Key (K)

    • Value (V)

During inference, K and V are cached for every token.

For every generated token:

KV cache size=(number of heads)×(sequence length)×(head dimension)

So:

  • More heads → better quality

  • More heads → larger KV cache

  • Large KV cache → slow & expensive inference

This becomes the main bottleneck in inference.

Different heads mostly differ in what they ask (Q), not in what they store (K, V). This leads to the idea:

  • Keep many Queries

  • Reduce how many Keys and Values we store

This is Attention Head Sharing.

Intuitive analogy. Without head sharing each person:

  • Has its own question

  • Has their own notebook of facts

With head sharing People:

  • Ask different questions

  • Read from the same notebook

(b) Multi-Query Attention (MQA)

All heads share the same K and V, but keep separate Q.

Heads: H1 H2 H3 H4
K,V: shared across all heads

(c) Grouped Query Attention (GQA)

A middle ground between MHA and MQA. Heads are divided into groups, and each group shares K and V.

Heads grouped:
Group 1 → shared K,V
Group 2 → shared K,V

Latent Attention / Latent KV (KV Compression)

Latent Attention (or Latent KV) is an inference optimization where Keys (K) and Values (V) for many tokens are compressed into a smaller number of latent representations, so the model attends to summaries of the past instead of every past token individually.

Even with:

  • KV cache

  • Head sharing (MQA / GQA)

KV cache still grows linearly with sequence length.

If a prompt has:

100,000 tokens

Then you must store:

100,000 K vectors
100,000 V vectors

This limits context length and memory scalability.

❌ Traditional KV cache

You remember every sentence from a book

K1, K2, K3, K4, ..., K100000
V1, V2, V3, V4, ..., V100000

✅ Latent KV cache

You remember key ideas only

Z1, Z2, Z3, ..., Zm (m << n)

Where:

  • Zi = a latent summary of many tokens

  • m is much smaller than n

Multi-Token Prediction (Token Prediction)

Multi-Token Prediction is an inference technique where a model predicts multiple future tokens in a single forward pass, instead of predicting only one token at a time.

Standard LLM decoding is autoregressive:

Predict token → append → predict next → append → ...

Input prompt

"I am going to"

Single-token decoding

Step 1 → school
Step 2 → today
Step 3 → .

This causes two major issues:

  • High latency (many sequential steps)

  • Poor GPU utilization (GPU waits between steps)

Idea: Instead of predicting 1 token per step

Predict: k tokens per step

Where k > 1.

Multi-token prediction (k = 3)

One step → ["school", "today", "."]

P(yt+1​,yt+2​,…,yt+k​∣context)
So:

  • It does one forward pass

  • But produces k different softmax outputs

Example

Suppose: We are at time step t

Context is: "I am going to"

We choose k = 3

One forward pass

The model processes the context once and produces k output heads (or k time positions).

Multiple logits (this is the important part)

Instead of producing one logits vector, the model produces:

logits₁ → yₜ₊₁

school: 0.80
home: 0.10
park: 0.10

logits₂ → yₜ₊₂

today: 0.70
now: 0.20
soon: 0.10

logits₃ → yₜ₊₃

.: 0.90
!: 0.05
?: 0.05

Each logitsᵢ is:

size = vocabulary size

Convert logits to probabilities

Each logits vector goes through its own softmax:

P(yt+1​∣context)=softmax(logits1​)P(yt+2​∣context)=softmax(logits2​)P(yt+3​∣context)=softmax(logits3​)
Final prediction: ["school", "today", "."]

Issues

If the first predicted token is wrong, then the second prediction is based on a wrong context so errors compound quickly

Example:

Wrong y₁ → y₂ and y₃ also wrong

Reduce Errors

(a) Confidence filtering

  • Only accept multi-token outputs if the probability is high.

(b) Hybrid decoding

  • Predict k tokens

  • Verify or regenerate if confidence drops

(c) Combine with speculative decoding

  • Small model proposes tokens

  • Large model verifies
